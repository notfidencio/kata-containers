# Kata Containers 4.4.0

This fork-only preview covers the changes after [4.3.1](4.3.1.md) through
upstream commit [`8fd86af`](https://github.com/kata-containers/kata-containers/commit/8fd86af5a8099749e0b4a01339abee7056ea1970).
`4.4.0` is a placeholder. The final release range and validation are still
to be confirmed.

This snapshot addresses failures that can survive a sandbox restart. The Rust
runtime can recover from more failed starts, track devices shared by multiple
containers, and find the root partition when an extension disk appears first.
Dragonball and Cloud Hypervisor get separate snapshot and storage fixes.
The containerd baseline moves to 2.3, and Substrate gets a dedicated guest.

## New features

### A dedicated guest for Substrate

Kata now builds a Debian trixie-slim guest and a Substrate-specific agent
for amd64 and arm64. The separate archive contains the root filesystem and the
standard Kata kernel. Substrate previously downloaded the full Kata archive
for those pieces. It continues to provide its own Cloud Hypervisor and
virtiofsd. The guest retains the diagnostic tools and package metadata needed
by the integration. [#14223](https://github.com/kata-containers/kata-containers/pull/14223)

### Up to 512 vCPUs with Cloud Hypervisor on x86_64

The x86_64 guest kernel now supports up to 512 CPUs, and both runtimes raise
the Cloud Hypervisor KVM limit to 512. Template validation and CPU resize
handling account for the new limit. Existing limits for MSHV and other
hypervisors remain in place. To configure a larger VM, check the effective
`default_vcpus` and `default_maxvcpus` and use a guest kernel built with the
higher CPU limit. [#13811](https://github.com/kata-containers/kata-containers/pull/13811)

## Breaking changes

### The containerd baseline moves to 2.3

The minimum containerd version in `versions.yaml` moves from 2.2 to 2.3.
The latest matrix entry remains 2.4. If you still run 2.2, plan the
containerd upgrade before rolling out this Kata snapshot. Check the running
daemon on nodes where the Kubernetes distribution provides containerd.
Updating Kata alone does not replace it. On a canary, check sandbox start,
image pull, and teardown with the RuntimeClasses you deploy. [#14183](https://github.com/kata-containers/kata-containers/pull/14183)

### Custom devkit bundles must include the host client

A devkit install now fails if it cannot install `kata-ctl`. The amd64 and
arm64 `kata-deploy` image builds require `kata-static-kata-ctl.tar.zst`,
and the NVIDIA GPU bundle now builds that archive. If you assemble your
own image or use `make nvgpu-tarball`, include the archive and verify the
installed client in the host's `bin` directory, normally
`/opt/kata/bin/kata-ctl`. [#14116](https://github.com/kata-containers/kata-containers/pull/14116), [#14147](https://github.com/kata-containers/kata-containers/pull/14147)

### Guest directory masks now take effect

The agent now masks directory entries in OCI `maskedPaths` using an empty,
read-only tmpfs. Previously, attempting to mount `/dev/null` over a
directory could leave it visible. Containers that relied on reading masked
guest paths such as `/sys/firmware` will see different behavior. The tmpfs
receives the OCI mount label when SELinux is enabled in the guest. Kata's
s390x protected-guest test uses a privileged container because it
deliberately reads `/sys/firmware/uv`. That setting is specific to the
test. [#14189](https://github.com/kata-containers/kata-containers/pull/14189), [#14213](https://github.com/kata-containers/kata-containers/pull/14213)

## Notable fixes

### Runtime startup, teardown, and device ownership

| Scenario | Effect | PR |
| --- | --- | --- |
| VMM start fails after spawning a process | The Rust runtime saves its process identity so it can confirm exit and clean up virtiofsd, the temporary rootless user, and runtime directories. | [#14143](https://github.com/kata-containers/kata-containers/pull/14143) |
| A sandbox restarts after a failed start | The Rust shim can reclaim a stale socket while preserving a live listener. It also removes its own socket when it stops serving. | [#14128](https://github.com/kata-containers/kata-containers/pull/14128) |
| Containerd invokes shim deletion in a fresh process | Cleanup recovers the original sandbox configuration. A Cloud Hypervisor node can clean up without validating the default QEMU binary it does not have. | [#14152](https://github.com/kata-containers/kata-containers/pull/14152) |
| Containers share hotplugged block or VFIO devices | The runtime tracks ownership and detaches shared devices after their final user is gone. VFIO hot-unplug can be retried. | [#13538](https://github.com/kata-containers/kata-containers/pull/13538) |
| QEMU gets auto-addressed disks and an explicitly addressed VFIO port | The runtime reserves explicit addresses first. This avoids a collision where a fourth extension disk could occupy the NVIDIA SNP GPU root-port slot. | [#14115](https://github.com/kata-containers/kata-containers/pull/14115) |
| Network teardown detaches devices asynchronously | A dedicated thread keeps namespace restoration on the thread that entered the namespace. Retry and timeout handling remains in use. | [#13886](https://github.com/kata-containers/kata-containers/pull/13886) |
| A passfd wait fails | The Rust runtime reports unknown exit status 255 and attempts normal stop and cleanup. A wait error could previously look like a successful process exit. | [#13963](https://github.com/kata-containers/kata-containers/pull/13963) |

The `cgroups-rs` updates also fix systemd unit reuse after a failed start
and a separate sandbox-start timeout seen on Rocky Linux 10.2 with
dbus-broker 36. For the latter, the library receives completion events and
matches them against the returned systemd job path. [#14128](https://github.com/kata-containers/kata-containers/pull/14128), [#14261](https://github.com/kata-containers/kata-containers/pull/14261)

### Snapshot restore, EROFS, and guest boot

**Dragonball.** Snapshot preparation captures device changes before
saving the virtio transport state. Restore preserves pending vsock reset
state and port allocation. Writable drives are restored after boot-time
devices so resource assignments remain stable even when managed drive IDs
or host paths differ. Template VMs skip the normal host upcall setup.
[#14075](https://github.com/kata-containers/kata-containers/pull/14075)

**Cloud Hypervisor and virtio-fs.** Cloud Hypervisor uses VMDK descriptors for
multi-layer EROFS container images, with layout helpers shared across VMMs
and temporary descriptors tracked for cleanup. The build stops forcing
`--thread-pool-size=1` on virtiofsd. That setting let a request finish
after device state was saved, leaving the restored guest with a stale
handle or hung operation. Dragonball's in-process virtio-fs is unaffected
by the virtiofsd change. [#13788](https://github.com/kata-containers/kata-containers/pull/13788), [#14134](https://github.com/kata-containers/kata-containers/pull/14134), [#14182](https://github.com/kata-containers/kata-containers/pull/14182)

**Virtio-blk root selection.** On QEMU, Cloud Hypervisor, and Dragonball,
the Rust runtime derives partition IDs from supported raw disk images.
It uses `root=PARTUUID=...` for the root partition and separate IDs for
dm-verity data and hash partitions where applicable. Extension disks can
probe first without becoming the selected root disk. The temporary s390x
guest-pull test skip was reverted with this fix. [#14161](https://github.com/kata-containers/kata-containers/pull/14161), [#14160](https://github.com/kata-containers/kata-containers/pull/14160)

**EROFS image creation.** The image builder flushes the EROFS data before
detaching the loop device. This prevents a build from reporting success
with a verity hash partition present and the filesystem data unwritten.
[#14159](https://github.com/kata-containers/kata-containers/pull/14159)

### Agent and policy generation

- The devkit debug console now terminates its shell regardless of which
  direction of the connection closes first. Reaping moves off the async
  worker, so single-vCPU guests can still answer RPCs and accept another
  session. [#14173](https://github.com/kata-containers/kata-containers/pull/14173)
- The runtime and agent wait for container removal to complete. This keeps
  removal and CoCo policy state in step and reduces the window in which
  resources can be left behind. [#14146](https://github.com/kata-containers/kata-containers/pull/14146)
- `genpolicy` computes supplemental group membership from the final
  container identity. If a container overrides the Pod identity, an
  inherited primary group no longer lingers merely because it was applied
  first. Explicit Pod supplemental groups and `fsGroup` still apply. [#14061](https://github.com/kata-containers/kata-containers/pull/14061)
- gRPC-to-OCI resource conversion preserves a provided PID limit so the
  agent can apply it to the container cgroup. [#14141](https://github.com/kata-containers/kata-containers/pull/14141)

### Deployment and GPU observability

- An empty annotation list stays an empty TOML array (`[]`). This avoids
  turning it into a list containing one empty string. [#14070](https://github.com/kata-containers/kata-containers/pull/14070)
- Replaying an install Job with identical generated CRI configuration or
  containerd drop-ins preserves modification times and avoids creating a
  new pending CRI restart. [#14066](https://github.com/kata-containers/kata-containers/pull/14066)
- The confined installer can append to CRI configuration files. The change
  grants the missing SELinux file permission. [#14140](https://github.com/kata-containers/kata-containers/pull/14140)
- DCGM exporter 4.8.4 restores the `DCGM_FI_DEV_XID_ERRORS` metric. Check
  that series after upgrading if your alerts depend on it. [#14117](https://github.com/kata-containers/kata-containers/pull/14117)

## Upgrading

1. **Check containerd first.** Bring nodes to the 2.3 baseline and verify
   sandbox startup, guest-pull if used, and sandbox removal on a canary.
2. **Check custom devkit artifacts.** For amd64 and arm64, verify the deploy
   image includes `kata-static-kata-ctl.tar.zst` and that the client exists
   on the host. Open a console, close it, and reconnect.
3. **Boot composable guests with the extension disks attached.** For measured
   images, confirm the expected rootfs and dm-verity partitions are selected.
   If you supply your own kernel command line, review fixed `/dev/vda` paths.
4. **Regenerate CoCo policies for workloads that override container identity.**
   Verify a representative guest-pull workload with the expected primary and
   supplemental groups and `fsGroup`. Include container removal in the check.
5. **Check workloads that read masked guest directories.** If a workload
   reads a path listed in `maskedPaths`, verify its behavior on the updated
   agent. The privileged s390x workaround is for the project's test only.
6. **Validate larger Cloud Hypervisor configurations with the deployed guest
   kernel.** Check both the boot and maximum vCPU settings before enabling
   workloads that need more than 256 vCPUs.

See [Upgrading](../Upgrading.md) and [Installation](../installation.md).
